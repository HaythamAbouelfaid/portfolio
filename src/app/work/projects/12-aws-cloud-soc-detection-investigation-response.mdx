## The Problem

Alerting alone does not establish a usable response process. A defensible security workflow also needs actionable case context, a human decision boundary, tightly scoped execution, a restoration path armed **before** mutation, and an audit trail that distinguishes automatic recovery from administrator intervention.

This project explores those concerns inside a personally controlled AWS lab.

## Architecture: Two Detection Paths

**CloudTrail API-history hunter.** A read-only Python tool examines selected management-event history against six explicit heuristics. These rules flag potentially interesting API behavior; they do not establish malicious intent without investigation.

**GuardDuty ingestion.** Findings are routed through EventBridge to a Lambda enrichment handler, normalized and stored in DynamoDB case records. SNS can notify the analyst. This path is separate from the Python hunting tool.

The analyst examines the resulting cases before any authorized response.

## Human Authorization Before Response

A finding's priority is not authority to mutate cloud infrastructure. The response plane uses a separate IAM reviewer identity, SigV4-signed requests and challenge/nonce checks. SQS decouples that authorization from downstream Lambda execution.

The browser is intentionally **read-only**. It does not expose approval or containment buttons, and a local mock walkthrough does not execute an AWS mutation.

## Canary-Only Execution and Recovery-First Ordering

The controlled test target was a disposable, unattached EC2 network interface owned by the personal lab. The response executor validated the approved request and canary scope, persisted the original security-group snapshot, and armed a one-time EventBridge Scheduler rollback **before** applying the quarantine security group.

A separately authorized rollback Lambda could later retrieve the saved baseline, restore the original SG and confirm the actual EC2 state before persisting a final status. This recovery capability was designed to remain available independently of new forward live-containment authorization.

## Security, Evidence and Limitations

Key design controls include scoped IAM permissions, separate human authorization, a disposable canary allowlist, snapshot-first execution, independent rollback, EC2 readback and DynamoDB/CloudWatch evidence.

The audit is **logically append-only by policy and role separation**, not cryptographically immutable hardware evidence. Out-of-band administrative actions require reconciliation. Some architecture-page network/encryption assurances were not independently established by the browser audit.

Source-code logging sanitization was merged in October, but its deployment to the running AWS Lambda packages was **not verified** as of the reviewed October 17 documentation. Current billing and the current AWS safe-mode state were also **not rechecked** by the mock-mode browser audit.

## Engineering Takeaways

- Preserve recovery capability before applying containment.
- Distinguish analyst triage from authority to act.
- Make synthetic tests, actual AWS readbacks and historical evidence easy to tell apart.
- Record failed and manual restorations accurately rather than rewriting them as success.
- Keep the portfolio UI read-only and minimize the exposure of private infrastructure details.
