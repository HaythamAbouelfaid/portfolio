1. Purpose and learning outcomes

A security-operations center should explain not only what activity looks suspicious, but also how evidence is evaluated, who authorizes response, how dangerous actions are bounded, and whether recovery is proven. This personal project connects those questions using AWS-native components, Python, Terraform, and a local Next.js read-only analyst cockpit.

It does not claim paid SOC employment, a production-grade managed detection-and-response platform, or a real attack against a customer workload. Controlled tests used a disposable, unattached lab network interface.

At the end of this guide, a learner should be able to diagram two detection sources, interpret a case lifecycle, explain least-privilege approval, describe pre-armed rollback, validate synthetic demo behavior, and distinguish a successful automated restoration from emergency manual recovery.

3. Threat model and trust boundaries

Assets to protect: AWS account permissions, raw event records, response approval tokens, original security-group state, the recovery schedule, audit integrity, and a user's browser session. The highest-risk operation is a live EC2 change; therefore normal use remains read-only, and mutation requires an explicit operator-owned workflow outside the browser.

Threats and failures considered: overprivileged API identities; forged or replayed approvals; the wrong account or target resource; logging of SQS receipt handles or nonces; a failed or delayed Scheduler invocation; manual out-of-band configuration changes; confusion between synthetic and live telemetry; leaking account/resource identifiers through screenshots.

Controls: narrow IAM roles, expected-account checks, isolated canary scope, nonce-bound reviewer authorization, zero browser mutation endpoints, durable baseline snapshots, pre-armed one-time rollback, independent recovery enablement, EC2 read-back, and audited manual reconciliation. Append-only audit is logical and policy-governed, not cryptographic or physically tamper-proof.

Security is layered. A high-severity case is evidence for review, not permission to modify infrastructure. A signed approval authorizes only the defined target and action, while the response executor verifies prerequisites again.

4. Architecture and event paths

Path A — CloudTrail history hunt: a read-only AWS session requests bounded CloudTrail LookupEvents management history. tools/cloudtrail_history_hunter.py parses event details in memory, emits metadata-only findings, and avoids persisting raw event bodies. A human reviews and classifies the resulting findings.

Path B — GuardDuty findings: GuardDuty → EventBridge → Lambda enrichment → DynamoDB case record. SNS can notify the analyst queue. This is separate from the CloudTrail hunter; describing the entire pipeline as a single six-rule real-time detector would be inaccurate.

Response path: escalated case → separate SigV4 reviewer approval → controlled API/state transition → SQS → response executor Lambda → durable baseline snapshot and one-time rollback schedule → EC2 canary SG change → automatic recovery Lambda → read-back and audit.

Visibility path: DynamoDB and bounded AWS read operations → server-side Next.js adapter → a local eight-view dashboard. The mock adapter supplies synthetic cases without cloud API calls; the AWS adapter is separate and read-only. Browser-originated live approvals and containment are intentionally unavailable.

5. Lab foundation, permissions, and safe setup

Use a dedicated, personally controlled AWS sandbox, not a production/customer account. Establish an AWS region, cost alerts and an administrator-approved teardown plan before creating billable resources. Prefer AWS IAM Identity Center sessions and role separation to long-lived access keys.

A practical progression is:

  1. Clone or inspect the repository and review README.md, infra/, tools/, scripts/, and apps/soc-console/.
  2. Run unit tests and offline fixtures without AWS credentials.
  3. Configure the local SOC console in DATA_SOURCE=mock mode and confirm the synthetic banner.
  4. Inspect Terraform files, IAM scopes and rollback behavior in a plan-only review. A Terraform plan can disclose account-specific metadata: keep plans private.
  5. Only if authorized to run your own bounded lab: independently approve an unattached disposable canary target, verify rollback arming and recovery paths, and keep explicit manual recovery procedures available.
  6. After any live test, verify AWS state read-back and return forward execution to safe mode while preserving recovery capability.

Do not copy IDs, ARNs, keys, nonces, original request files or private CloudWatch messages from another account. In particular, public documentation should never instruct someone to paste real approval nonces or run unrestricted EC2 mutations.

6. Six Python CloudTrail detection heuristics

Source implementation: tools/cloudtrail_history_hunter.py. The hunter operates on management event history. It is not an exhaustive behavior detector, SIEM, network packet sensor or proof of compromise. Its exact rules are:

Rule Severity Trigger logic
ROOT_PRINCIPAL_ACTIVITY High CloudTrail userIdentity.type == Root
CONSOLE_LOGIN_FAILURE Medium ConsoleLogin with responseElements.ConsoleLogin == Failure
ACCESS_DENIED_ATTEMPT Low Error code includes AccessDenied, Unauthorized or OperationNotPermitted
CLOUDTRAIL_CONFIGURATION_CHANGE High Successful specified CloudTrail configuration mutation API
IAM_PRIVILEGE_MODIFICATION High Successful specified IAM policy or trust-policy modification API
S3_SECURITY_POLICY_CHANGE Medium Successful bucket policy, ACL or public-access-block change API

The real code defines specific event-name allowlists and checks the AWS service source before firing the latter three rules. A single event can trigger more than one heuristic. Failure/denied signals alone are not proof of malicious intent.

Run the hunter safely against a sanitized fixture:

cd aws-cloud-soc-automated-response
python3 tools/cloudtrail_history_hunter.py --fixture path/to/sanitized-events.json

The fixture must have an Events array shaped like CloudTrail lookup results. Live read-only querying additionally requires an expected account ID and AWS profile, but is not necessary for this educational exercise. Never include the real 12-digit ID in screenshots or public transcripts.

Illustrative, not executable finding record:

{"rule":"IAM_PRIVILEGE_MODIFICATION","severity":"HIGH", "event":"AttachRolePolicy", "service":"iam.amazonaws.com", "time":"<redacted UTC>"}

Validate by testing rule matching, negative cases, severity classification and suppression of raw CloudTrailEvent/identity detail in output.

7. GuardDuty, EventBridge, Lambda, DynamoDB, SNS

GuardDuty produces managed threat-detection findings. EventBridge filters/routs matching events. A Lambda enrichment handler validates and normalizes selected metadata, then writes a durable DynamoDB case. SNS can deliver an analyst notification. Each component has a distinct role; separating them makes it easier to audit data minimization and error handling.

In a synthetic exercise, feed a sanitized finding through the offline transformation tests and verify that the resulting case has a stable identifier, event source, severity, matched rule/type, timestamps and analyst-readable summary. Sensitive identifiers and credentials must be scrubbed before showing evidence in a browser.

Operationally, account for duplicate events, eventual consistency, expired cases (TTL), failed Lambda invocations and downstream notification errors. A notification success is not equivalent to a completed investigation or a containment approval.

9. IAM reviewer, SigV4 and least privilege

The approval subsystem intentionally separates investigating from authorizing and executing. A triaged/escalated finding may lead to a specific proposal. A dedicated reviewer identity authenticates a signed API request, including a fresh challenge/nonce and request-bound parameters. The backend checks the request and its allowed target; the execution worker separately enforces scoped containment.

Why not a browser Approve button? A local read-only browser must not hold privileged AWS tokens or expose a mutation endpoint. The dashboard's Approval Gate page documents these boundaries rather than executing authorization itself.

In threat modeling, validate: wrong reviewer role, stale nonce, changed parameters, expired approval, duplicate requests, unsupported target, inadequate IAM and attempted browser mutation. Denied execution should remain logged as a failure rather than be silently retried as success.

10. Recovery-first containment sequence

Containment changes are potentially disruptive. The lab therefore implemented a recovery-first sequence:

  1. Reviewer authenticates and approves the specific lab-only action; request enters a queue.
  2. The response worker confirms account, VPC, target ENI, tags, status and allowed original/quarantine security groups.
  3. The worker reads and durably stores the original security-group configuration.
  4. Before modifying the ENI, it arms a one-time EventBridge Scheduler rollback and records its identity/deadline.
  5. Only then does the worker apply the temporary quarantine security group and verify actual EC2 read-back.
  6. At the configured time (with ordinary scheduler/invocation latency), the independent recovery Lambda reads the saved baseline, restores the original group and verifies the EC2 read-back.
  7. The durable request and audit trail distinguish success, failure, and emergency administrator restoration.

The configured timer is a policy, not a hard real-time SLA. A 60-second configured schedule produced an 84-second measured interval in the historical acceptance test.

Do not adapt the lab containment mutation commands to real infrastructure without an independent authorization, rollback and recovery plan. This guide deliberately excludes live mutating commands.

The primary source is docs/phase05/02_AUTOMATED_ROLLBACK_LIVE_ACCEPTANCE.md in the private engineering repository. Independent historical AWS checks corroborated the request record, Scheduler invocation, recovery Lambda logs, actual EC2 group change and restoration, and durable audit evidence.

Event Historical UTC time

Quarantine SG verified by EC2 read-back 18:08:45

Scheduler-triggered recovery Lambda invocation 18:10:05

Measured containment-to-restoration: 84 seconds. The request was classified ROLLED_BACK, with trigger AUTOMATIC_SCHEDULED_ROLLBACK, method WORKER_EC2_MUTATION, and verified restoration status. No administrator performed the restoration between containment and recovery.

Earlier requests had emergency administrator restoration and later reconciliation. Those events are not automated rollback successes. Do not combine the historical records or replace their failure labels with the outcome of the successful test.

12. Audit integrity, failure recovery and limitations

DynamoDB stores response/approval history under authorization and conditional-write policies. The system is designed as a logical append-only audit: it is not an immutable cryptographic ledger. An out-of-band administrator who directly changes EC2 state can create a physical-versus-audit discrepancy until reconciliation is performed.

Failure examples and responses: missed schedule → inspect recovery Lambda, scheduler record, DDB request and EC2 read-back; permissions-denied containment → stop and investigate IAM scope; incorrect original snapshot → fail closed before mutation; unauthorized manual restore → verify EC2 state and write a clearly labeled reconciliation event. Manual recovery must remain manual in the audit.

Current limitations: the cockpit is localhost only; mock datasets are fixed demonstrations; audit phase filters have a UI bug; older mock values are not updated to the final one-minute test; some claimed encryption/network controls need IaC verification; source-only CloudWatch SQS-log sanitization was committed but its AWS deployment was not independently confirmed by the browser audit. A final security review must not overstate these boundaries.

15. Operational closeout, privacy and cost review

Before any public publication: check screenshots for IDs, ARNs, roles, account numbers, IPs, request IDs, nonce values, raw JSON, credential material, and other private details. Cropping alone can leave small identifiers visible. Replace them with opaque masks and inspect the flattened output.

Before any independent new lab test: confirm explicit authorized target, available rollback and manual recovery, correct account/region, planned costs and clean initial state. The final production video deliberately used a historical result so no second mutation test was needed.

After a live test: verify the original group restored; zero orphaned schedules; no unresolved requests; response Lambda execution disabled; recovery remains enabled; Terraform and DDB state consistent. The October 13 acceptance report documented this for that date, not a continuous guarantee afterward.

Costs should be read from current account billing/Cost Explorer when claimed. Do not state that AWS resources cost zero based solely on a mock screen or estimated free-tier fit. CloudTrail, GuardDuty, logs, DynamoDB, Scheduler, S3 and data transfer may incur charges.
